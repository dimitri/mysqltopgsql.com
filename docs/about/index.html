pgloader in Practice

What actually happens when pgloader migrates your data — the command, the casting rules, and a real migration report.

When migrating from MySQL to PostgreSQL, you need to implement a proper Project Methodology. Your migration budget is then splitted in those 4 areas:

Migrating the Data

pgloader implements fully automated migration from MySQL to PostgreSQL in a single command line:

$ pgloader mysql://user@host/dbname pgsql://user@host/dbname

More complex scenarios are of course possible:

$ pgloader f1db.load

With the following f1db.load command:

load database
  from mysql://root@localhost/f1db
  into pgsql:///f1db
  with concurrency = 2,
       multiple readers per thread,
       rows per range = 50000
       prefetch rows = 1000000;

As the goal for pgloader is for the migration to be fully automated and part of your CI/CD nightly jobs, it is also possible to add type casting rules to the command.

Here’s a more complex example:

load database
     from mysql://root@unix:/tmp/mysql.sock:3306/pgloader
     into postgresql://dim@localhost/pgloader

 alter schema 'pgloader' rename to 'mysql'

 CAST column base64.id to uuid drop typemod drop not null,
      column base64.data to jsonb using base64-decode,

      type decimal when (and (= 18 precision) (= 6 scale))
        to "double precision" drop typemod

 before load do $$ create schema if not exists mysql; $$;

In this example you can see that we chose to cast the column id of the base64 table to the uuid type in PostgreSQL. Read the pgloader reference documentation for all the details about the casting rules.

Migrating the Service

This needs to be carefully planned to. Check about your allowed downtime and if the migration runs fully within that window, as it’s the easier to implement, always.

Other option such as incremental migration or replication from MySQL to PostgreSQL are possible. They come with complexity that is best avoided, though. Keep it as Simple as you can.

Often enough, the source database contains tables that receive very low DML trafic (that’s insert, update, and delete). Then you can migrate those tables ahead of schedule, and only migrate the live tables during the downtime window.

To implement that, pgloader implements the following clauses in its command language:

INCLUDING ONLY TABLE NAMES MATCHING ~/film/, 'actor'
EXCLUDING TABLE NAMES MATCHING ~<ory>

Use that to split your migration into the archive parts and the live parts if you have to.

Opportunity Cost

While you’re working on the migration, you are not implementing those new shiny features that the Product department is waiting for. Everybody needs to understand that you’re busy migrating, and that the new system is going to be so much better off using PostgreSQL.

about pgloader

pgloader is the open-source tool named in nearly every MySQL-to-PostgreSQL migration guide published — it automates schema translation, data loading, and casting rules in a single command line. This site is written by pgloader's author.

Everything here — the methodology, the FAQ, the course — comes from actually running migrations, not from reading about them. See the project itself at pgloader.io.

FAQ
Is this actually free, or is that a trick?
The Continuous Migration core — why to migrate, the budget, the target architecture, and pg_auto_failover — is free, permanently, no card required. The hands-on pgloader mechanics, casting rules, and stored-procedure porting are the paid course.
Do I need a PostgreSQL background to use this?
No — this is written for developers and DBAs coming from MySQL. Where PostgreSQL behaves differently, that's the whole point of the FAQ section.
Does pgloader handle Oracle or MS SQL Server too?
Yes, MS SQL Server is a supported source today; Oracle is on pgloader's roadmap, not yet shipped. This site is scoped to MySQL specifically.
I run pgloader in production — should I be paying for something?
If pgloader is part of your production workflow, its maintenance is worth funding — see the Support pgloader page.
